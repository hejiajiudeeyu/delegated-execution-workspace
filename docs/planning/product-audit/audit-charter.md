# 产品与架构深度审查章程（Audit Charter）

Created: 2026-07-04 · 供独立审查 loop 执行。**审查是只读的**：产出文档与修订建议，不改任何代码，可与开发 loop 并行。

## 目的

owner 对产品完成度不自信，快扫（`functional-inventory-v0.md`）已给出 v0 判断，其中多项标 ⚠️ 待验证。本审查要把 v0 升级为有证据的 v1，并产出可执行的修订版 roadmap。

## 审查维度与关键问题

### D1 用户旅程完备性（产品）
逐角色走查代码级真实路径（不是文档宣称的路径）：
- Caller：注册 → 获得 PTS（**现在到底能不能自助?**）→ 发现热线 → 调用 → 查账 → key 丢失恢复。
- Responder：注册 → 上架 → 审核等待期体验 → 收益查询 → 更新热线版本 → 下架。
- Operator：从零部署 → 首次解锁 → 日常审核/计费/巡检 → 事故恢复。
每条旅程输出：断点清单（用户卡死处）、绕行成本（需要人工介入处）。

### D2 API 面完整性与一致性
- 全量枚举 platform-api 路由 × 方法 × 鉴权级别 × 分页/幂等/错误码规范一致性；
- v1/v2 并存的实际差异与弃用策略缺失的影响；
- 缺失接口清单：webhook/callback、用户级 key 管理、自助充值、通知拉取等——逐项判断"现在留接口"vs"以后再加"的成本差。

### D3 数据与存储
- sqlite/DATABASE_URL 双轨的真实状态；迁移机制有无；并发写入边界；备份策略；
- 核心表模型能否承载：多 key/租户、热线多版本、异步任务状态。

### D4 架构与可扩展性
- platform-api（单文件路由）、cli.js（1900 行）的模块化拆分方案与时机建议；
- contracts 发布管线设计（本地 workspace ↔ npm 漂移如何被 CI 门禁拦住）；
- 传输层抽象是否真的可插拔（email transport 字段存在但未验证）。

### D5 安全
- 威胁面清单：公网 API 滥用、审核绕过、计费竞态（hold 并发）、admin key 单点、gateway bootstrap secret 强度、注册无验证的女巫攻击；
- 每项给出：现状、风险等级、最小缓解。

### D6 质量基建
- e2e 套件修绿方案；浏览器层自动化的最小可行方案（哪怕 smoke 一条）；CI 必须门禁哪些（发布挡板）。

## 方法要求

- 结论必须挂证据（文件:行 / 命令输出 / CI run）；推测必须标注"推测"；
- 与 v0 清单逐条对账：确认 / 推翻 / 修正；
- 不贪多：每维度产出"前 5 个最重要发现"，长尾进附录。
