## 0. 为什么是这三项 / 目标

审计结论（`functional-inventory-v1.md` 发现 1/2、`security-review.md`）：**闭环骨架真、经济闭环断**。三项合起来把"注册→有账户→能自助充值→调用→责任方真收到钱"补成闭环：

- **P0.5-a 注册即建租户**：现在 `registerCallerUser` 不建计费租户，查余额直接 `TenantNotFoundError`。
- **P0.5-b 自助获得 PTS**：现在充值仅 admin（`server.js:3694`），新 Caller 卡死在"没有 PTS"。
- **P0.5-c 责任方收益入账**：结算处 `debit` 是 `deltaCents:0`（`server.js:800-807`），caller 被扣的 `usage.total_cents` **没有任何 `responder_earn` credit 对应，凭空进平台**。

三项都是平台侧低成本改动，验收标准 = 一个全新 caller 能自助注册、拿到 PTS、调用一次热线，且责任方 owner 的余额增加了实际消费额。

## 1. 核心设计决策（建议 owner 先拍板）

这三个决策影响实现形状，建议先定：

| 决策 | 选项 | 本方案默认（建议） | 理由 |
|---|---|---|---|
| **D-1 责任方收益入谁的账** | (a) responder.owner_user_id 的 tenant / (b) 给 responder 建独立 tenant | **(a) owner_user_id** | tenant_balance schema 已有 `used_as_caller_cents` 与 `earned_as_responder_cents` 双字段（`002:46-47`），同一账户既能花也能赚，最符合现有模型；无需新表 |
| **D-2 平台是否抽成** | (a) 全额入责任方 / (b) 扣平台佣金后入账 | **(a) 全额（佣金留作后续项）** | 最小改动先把"收益从 0 到 1"打通；佣金是独立特性，可在有 earn 分录后再加一条 platform_fee 分录 |
| **D-3 直接 credit 还是 pending_credit** | (a) settle 时直接 credit / (b) 记 pending_credit 待释放 | **(a) 直接 credit** | billing-store 虽有 pending_credit 字段与 `pending_credit_release/revoke` ledger kind（`002:8-9`），但 **platform-api 从不传 pendingDeltaCents**（grep 无调用方）——pending 全链路是空的，走它要额外实现释放触发；直接 credit 是最短路径 |

> 若 owner 对 D-2 选 (b) 抽成 或 D-3 选 (a) pending，本方案的 P0.5-c 需相应扩展（附 §7 变体说明）。

## 2. P0.5-a 注册即建租户

**改动点**：`server.js` 的 `/v1/users/register` 处理器（`:2830-2844`）或 `registerCallerUser`（`:1202-1224`）。

**为什么**：`createTenant` 是幂等的（`ON CONFLICT (tenant_id) DO NOTHING`，`billing-store:328`），可安全在注册成功后 ensure。否则赠点/自助充值/收益入账都无账可落。

**建议实现**（在路由处理器里，`registerCallerUser` 之后、`sendJson` 之前）：

```js
// server.js 路由 /v1/users/register，registerCallerUser 成功后
if (state.billingStore) {
  try {
    await state.billingStore.createTenant(user.user_id, user.created_at);
  } catch (error) {
    // createTenant 幂等；失败不应阻断注册，记日志即可
    console.error("[register] ensure tenant failed", user.user_id, error);
  }
}
```

**注意**：放在路由层而非 `registerCallerUser` 内，因为后者是同步纯函数、无 billingStore 引用（保持其可测性）。responder 注册路径（`registerResponderIdentity` → owner_user_id）同理需 ensure owner 的 tenant——但 P0.5-c 会在 settle 处兜底 ensure，故此处可只覆盖 caller 注册。

**测试**：`tests/integration/platform-api-billing.integration.test.js` 加一例——注册新 caller 后，不经 admin 建租户，直接 `GET /v1/tenants/me/balance` 应返回 200 且 `credit_balance_cents: 0`（当前会 404/`TenantNotFoundError`）。

## 3. P0.5-b 自助获得 PTS

**两个选项**，建议 **B1 注册赠点**（最小）为第一步，**B2 自助充值路由**为完整解：

### B1 注册赠点（最小，先做）
在 P0.5-a 的 `createTenant` 之后，若配置了赠点额度则记一笔 recharge：

```js
const signupGrant = readNumberEnv(process.env.SIGNUP_GRANT_CENTS, 0);
if (state.billingStore && signupGrant > 0) {
  try {
    await state.billingStore.createRecharge({
      recharge_id: `grant_${user.user_id}`,     // 幂等键，防重复赠点
      tenant_id: user.user_id,
      amount_cents: signupGrant,
      currency: "PTS",
      provider: "signup_grant",
      recorded_at: user.created_at
    });
  } catch (error) {
    if (!(error instanceof RechargeDuplicateKeyError)) console.error(...);
  }
}
```
- 默认 `SIGNUP_GRANT_CENTS=0`（不赠），public-stack env 可设个位数（如 200 PTS 够试调几次）。
- `recharge_id` 用确定性 `grant_<user_id>` 保证一个用户只赠一次（`createRecharge` 有重复检测，`billing-store:626-634`）。

### B2 自助充值路由（完整）
新增 `POST /v1/tenants/me/recharges`（caller-scope），复用 admin recharge 的逻辑：

```js
if (method === "POST" && pathname === "/v1/tenants/me/recharges") {
  const auth = requireCaller(req, res, state);
  if (!auth) return;
  const billingStore = requireBillingStore(res);
  if (!billingStore) return;
  const body = await parseJsonBody(req);
  if (!body.recharge_id || body.amount_cents === undefined) { /* 400 */ }
  // 自助充值必须有额度上限/风控——见风险 §8
  const recharge = await billingStore.createRecharge({
    recharge_id: body.recharge_id,
    tenant_id: auth.user_id,       // 关键：只能给自己充
    amount_cents: body.amount_cents,
    currency: body.currency || "PTS",
    provider: "self_service",
    recorded_at: new Date()
  });
  sendJson(res, recharge.httpStatus || 201, { tenant_id: auth.user_id, recharge });
}
```
- **注意**：真实产品里"自助充值"要接支付；PTS 阶段无支付渠道，故 B2 本质是"自助兑换/试用额度",**必须加额度上限与频率限制**（否则等于无限印钞，见 §8）。因此 **B1（固定赠点）比 B2 更安全**，建议 B1 先上、B2 待支付渠道就绪。

**测试**：B1——新 caller 注册后（`SIGNUP_GRANT_CENTS=200`）balance 应为 200；重复注册同 email 不叠加（幂等）。B2——caller 只能给自己充、不能指定他人 tenant_id。

## 4. P0.5-c 责任方收益入账（🔴 核心）

**精确机制**（审计定位）：settle 时（`applyTerminalBillingIfNeeded` COMPLETED 分支，`server.js:786-812`）：
- hold 阶段已从 caller 扣 `hold_amount_cents`（max_charge）；
- settle 把找零 `refundDelta = hold - usage.total_cents` 退回 caller（`:790-798`）；
- `debit` 分录是 `deltaCents:0`（`:800-807`）——仅标记，不动钱；
- **净效果**：caller 少了 `usage.total_cents`，但**无任何账户多这笔钱**。

**建议实现**：在 settle 成功、`debit` 之后、设置 `request.billing.state="settled"` 之前，补一笔责任方 credit：

```js
// server.js:807 之后
const responder = state.responders.get(request.responder_id);
const earnTenantId = responder?.owner_user_id || null;   // D-1: 收益入 owner 账
let earn = null;
if (earnTenantId && usage.total_cents > 0) {
  // 兜底 ensure owner tenant（幂等），覆盖匿名/老数据 responder
  await state.billingStore.createTenant(earnTenantId);
  earn = await state.billingStore.applyBalanceDelta({
    tenantId: earnTenantId,
    deltaCents: usage.total_cents,        // 正数 = credit；D-2 默认全额
    kind: "credit",
    direction: "responder_earn",          // 触发 earned_as_responder_cents 累计（billing-store:414）
    requestId: request.request_id,
    recordedAt: body.finished_at || new Date()
  });
}
request.billing.state = "settled";
request.billing.earn_ledger_id = earn?.ledger_id || null;   // 新增字段，留痕
// ... 其余不变；billingEvent 可加 earn_ledger_id
```

**边界处理**：
- `owner_user_id` 为空（理论上不该，registerResponderIdentity 总会赋值）→ 跳过 credit，记日志（收益无主，需人工）。
- owner 无 tenant → `createTenant` 幂等兜底先建。
- `usage.total_cents === 0`（免费热线）→ 不记 earn。
- **原子性提醒**：earn credit 与 caller debit 不在同一事务（分属两次 applyBalanceDelta），继承 D3.4 的崩溃窗口——若 earn 前崩溃，caller 已扣、responder 未收。可接受（金额小、可对账补），但 §8 记为已知限制；彻底解决需把 settle 的多笔分录并入一个 tx（billing-store 的 `withClient` 支持传 tx，是后续优化）。

**测试**（集成，最关键的验收）：
```
1. 两个身份：callerA（owner）注册 + recharge 1000；responderR 由 callerA 拥有（owner_user_id=callerA.user_id），上架热线并 admin approve+enable。
   —— 简化：可让同一 user 既是 caller 又 enable-responder（owner=自己）。
2. callerB 注册 + recharge，call-hotline 调 responderR 的热线，usage.total_cents=50，走到 BILLING_SETTLED。
3. 断言：callerB balance 减少 50；callerA（responder owner）balance 增加 50，且 ledger 有一条 direction=responder_earn / kind=credit / amount_cents=50；balance.windows 的 earned_as_responder_cents=50。
```
这条测试同时守护 D3.6 的收益承载与本项。

## 7. D-2/D-3 变体（若 owner 改决策）

- **D-2 抽成**：在 §4 的 earn 前算 `const fee = Math.round(usage.total_cents * FEE_RATE); const net = usage.total_cents - fee;`，credit `net` 给 owner，另记一笔 `kind:"platform_fee"/direction:"system"`（需在 migration 的 `ledger_kind` ENUM 加 `platform_fee`，属 schema 变更→按仓库规则先动 contracts/迁移）。
- **D-3 pending**：earn 用 `pendingDeltaCents: usage.total_cents, deltaCents: 0, kind:"credit"`，另需一个"释放"触发（如责任方无争议期后 `pending_credit_release`）——全链路当前为空，工作量显著大于直接 credit，不建议作为第一步。

## 8. 风险与已知限制

| 风险 | 说明 | 缓解 |
|---|---|---|
| 自助充值=无限印钞（B2） | PTS 无支付背书，开放自助充值等于任意造币 | B1 固定赠点优先；B2 加额度上限+频率限制，或等支付渠道 |
| 赠点女巫（配合 D5 S6） | 注册无验证 + 赠点 = 批量薅点 | 赠点额度设小（够试调不够滥用）；配合收紧注册限速（D5 S6）；grant_id 幂等防同用户重复 |
| earn/debit 非原子（D3.4） | settle 多笔分录跨 tx，崩溃可致 caller 扣、responder 未收 | 金额小可对账补；彻底解需并入单 tx（billing-store `withClient` 支持传 tx，后续优化） |
| 匿名 responder 收益无主 | owner_user_id 为随机 id、无真人 | §4 兜底 ensure tenant；根治=responder 注册要求已认证 caller（D5 S6 同向） |

**回滚**：三项均为叠加式（新增分录/新增 ensure），无 schema 破坏性变更（D-2 抽成除外）；回滚 = 撤代码即可，已入账的 earn 分录留在 ledger 不影响 caller 侧。
